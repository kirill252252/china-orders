# Тезисы для пояснительной записки курсовой работы

## Тема
«Проектирование и разработка веб-приложения для автоматизации заказов с китайских маркетплейсов»

## 1. Актуальность
- Рост кросc-бордер e-commerce: российские покупатели всё чаще заказывают товары с китайских площадок (Taobao, Tmall, 1688, Pinduoduo, JD, Poizon).
- Сложность самостоятельного заказа: языковой барьер, отсутствие прямых платежей, логистика, таможня.
- Спрос на посреднические сервисы (покупка за заказчика, консолидация, доставка до двери).
- Необходимость автоматизации рутинных операций: парсинг товаров, расчёт стоимости, отслеживание статусов, учёт финансов.

## 2. Цель работы
Проектирование и разработка полнофункционального веб-приложения (frontend + backend + БД) для автоматизации бизнес-процессов посреднической службы закупок на китайских маркетплейсах.

## 3. Задачи
1. **Анализ предметной области** — изучение бизнес-процессов закупки, доставки, таможенного оформления, выявление ролей и сценариев использования.
2. **Проектирование БД** — нормализованная схема (3НФ), 14 таблиц, FK/PK/UNIQUE/CHECK, индексы, триггеры аудита, PL/pgSQL функции расчёта, представления для отчётности.
3. **Архитектура backend** — REST API (Express), модульная структура, JWT + Refresh токены, RBAC, валидация Zod, параметризованные SQL, миграции, сиды.
4. **Интеграция с маркетплейсами** — абстракция `MarketplaceProvider` для расширяемого импорта товаров по URL (MockProvider для демо).
5. **Бизнес-логика заказов** — корзина, расчёт стоимости (курс + комиссия + доставка), FSM статусов с запретом недопустимых переходов, мок-оплата, история изменений.
6. **Кэширование и rate limiting** — Redis для refresh-токенов, курсов валют, каталога, защиты от брутфорса.
7. **Frontend** — SPA (React, Vite, Router), адаптивные страницы для трёх ролей, CSS Modules, состояния загрузки/ошибок, таймлайн заказа.
8. **DevOps** — Docker Compose (postgres, redis, backend, frontend), healthchecks, volumes, .env конфигурация.
9. **Тестирование** — интеграционные тесты (auth, orders, pricing, status transitions) на Vitest + Supertest.
10. **Документация** — ER-диаграмма, описание БД, API reference, README, тезисы курсовой.

## 4. Обоснование выбора стека

| Компонент | Выбор | Обоснование |
|-----------|-------|-------------|
| **Frontend** | React + Vite | Стандарт индустрии, большой экосистема, HMR, быстрая сборка |
| **CSS** | CSS Modules | Без runtime-оверхеда, изоляция стилей, нет зависимости от UI-китов |
| **Backend** | Node.js + Express | Единый язык (JS) на фронте и бэке, минималистичный, гибкий middleware |
| **БД** | PostgreSQL 16 | Зрелая СУБД, поддержка JSON, оконных функций, триггеров, PL/pgSQL, 3НФ |
| **Драйвер БД** | `pg` | Нативный, быстрый, пулинг соединений, параметризованные запросы |
| **Миграции** | SQL-файлы + раннер | Полный контроль схемы, версионирование в git, воспроизводимость |
| **Redis** | `ioredis` | Продвинутый клиент, кластеризация, Lua-скрипты для rate limiting |
| **Валидация** | Zod | Type-safe схемы, infer types, композиция, отличная DX |
| **Auth** | JWT + httpOnly cookie | Stateless access, защита от XSS (refresh в cookie), короткий TTL access |
| **Безопасность** | Helmet, CORS, bcrypt | Best practices: CSP, HSTS, защита от CSRF, стоимость хеша 12 |
| **Тесты** | Vitest + Supertest | Быстрый, ESM-совместимый, совместим с Jest API |
| **Контейнеризация** | Docker Compose | Изоляция сервисов, воспроизводимость окружения, простое развёртывание |

## 5. Архитектурные решения

### Backend — модульная монолитная архитектура
```
src/
├── config/         # env, DB pool, Redis client
├── controllers/    # тонкие обработчики → сервисы
├── middleware/     # auth, rbac, validate, errorHandler
├── models/         # репозитории: чистый SQL, транзакции
├── routes/         # композиция роутеров по доменам
├── services/       # бизнес-логика (pricing, orders, marketplace)
├── utils/          # jwt, errors, helpers
└── validators/     # zod схемы для каждого эндпоинта
```

### База данных — нормализованная, с бизнес-логикой в БД
- **Триггер `trg_order_status_history`** — гарантированная аудитория смены статусов (независимо от кода приложения).
- **Функция `fn_calculate_order_total`** — централизованный расчёт, используется и при создании заказа, и при пересчёте админом.
- **Представления `v_manager_queue`, `v_orders_summary`** — готовые выборки для дашбордов, избегают дублирования JOIN-логики.
- **Чек-констрейнты** — защита данных на уровне БД (цена > 0, вес ≥ 0, валидные переходы статусов через код).

### Аутентификация — JWT Access (15 мин) + Refresh в Redis + httpOnly cookie
- Access токен хранится в памяти браузера (не в localStorage) → защита от XSS.
- Refresh токен — httpOnly, SameSite=Lax, Secure в prod → защита от CSRF/XSS.
- Инвалидация при логауте / смене пароля / блокировке пользователя — удаление из Redis.

### Импорт товаров — Strategy Pattern
```javascript
interface MarketplaceProvider {
  parseUrl(url): { marketplaceCode, externalId }
  fetchProduct(externalId): ProductData
}
```
- `MockProvider` — возвращает демо-данные для разработки и защиты.
- Реальные провайдеры добавляются без изменения контроллера (OCP).

### Расчёт стоимости — чистая функция с параметрами из БД
```javascript
totalRub = subtotalCny * rate * (1 + commission/100) + deliveryCost(weightKg)
```
- Курс — из `exchange_rates` (кэш Redis 1ч).
- Тариф — подбор по весу из `delivery_tariffs`.
- Все входные параметры версионируются в заказе (`exchange_rate_used`, `commission_percent`).

### FSM статусов заказа — валидация переходов в коде + БД
- Матрица допустимых переходов в конфиге/коде.
- Триггер БД пишет историю при любом изменении `status_id`.
- Финальные статусы (`delivered`, `cancelled`) — запрет дальнейших изменений.

## 6. Возможное развитие (Roadmap)

### MVP+ (ближайшие итерации)
1. **Реальные провайдеры** — реализация парсинга Taobao/1688/Poizon через Puppeteer/Playwright или API (где есть).
2. **Платёжные шлюзы** — интеграция ЮKassa/СБП/Т-Банк, вебхуки `/webhooks/payment`.
3. **Уведомления** — Email (nodemailer), Telegram-бот, WebPush для смены статусов.
4. **Файлы/документы** — загрузка чеков, накладных, фото товаров на складе (S3/MinIO).
5. **Консолидация** — объединение нескольких заказов в одну посылку, пересчёт доставки.

### Масштабирование
1. **Микросервисы** — выделение `marketplace-service`, `pricing-service`, `notification-service`.
2. **Message Queue** — RabbitMQ/Kafka для асинхронных задач (парсинг, вебхуки, экспорт 1С).
3. **Read Replicas** — разделение чтения/записи для аналитики.
4. **Кэширование каталога** — Redis + инвалидация при обновлении товаров.
5. **Поиск** — PostgreSQL `tsvector` → Elasticsearch/Meilisearch для полнотекстового поиска.

### Аналитика и BI
1. **OLAP кубы** — ClickHouse для быстрых отчётов по продажам, маржинальности, срокам.
2. **Дашборды** — Grafana/Metabase для менеджеров и владельца.
3. **ML** — предсказание срока доставки, рекомендации товаров, детекция аномалий цен.

### Удобство пользователей
1. **Telegram Mini App / WebApp** — оформление заказов прямо в Telegram.
2. **Браузерное расширение** — кнопка «Заказать через нас» на страницах товаров Taobao/1688.
3. **Мобильное приложение** — React Native / Expo на базе существующего API.
4. **Мультивалютность** — поддержка KZT, BYN, USD с автоматическими курсами ЦБ РФ.

### Администрирование
1. **Audit Log** — полная история действий админов (кто, что, когда изменил).
2. **Feature Flags** — запуск новых функций для части пользователей.
3. **Sentry / OpenTelemetry** — трассировка, метрики, алерты.

## 8. Заключение
Проект демонстрирует полный цикл full-stack разработки: от проектирования БД и API до контейнеризации и тестирования. Реализованная архитектура позволяет расширять функционал (новые маркетплейсы, платёжки, уведомления) без рефакторинга ядра. Качественная нормализация БД, использование триггеров и функций в PostgreSQL, правильная работа с токенами и кэшем — соответствуют практикам production-разработки.
